# Архитектура и устройство реализации

Документ для того, кто будет поддерживать проект. Читать вместе с `README.md` (как запускать)
и doc-комментариями `//!` в начале каждого модуля (там — «зачем этот файл»).

## 1. Принципы

1. **Слои зависят только вниз.** Геометрия и модель ничего не знают про маршруты, маршруты —
   про расстановку, логика редактора — про Slint.
2. **Логика отдельно от UI.** Всё, что можно проверить без окна, лежит в обычных Rust-модулях
   с unit-тестами. Slint-слой тонкий и «глупый»: получает готовые строки и числа.
3. **Данные — обычные структуры.** Нет трейт-объектов и колбэков в модели; состояние можно
   клонировать, сериализовать и сравнивать в тестах.
4. **Единицы.** Метры, ось Y вверх, углы в радианах против часовой стрелки. Пиксели существуют
   только в `viewport`/`scene`/`ui`.

## 2. Карта крейтов

```
                 ┌────────────┐
                 │  wh-core   │  Point, Polygon, OrientedRect, Warehouse, Shelf,
                 │            │  Product, Placement, ShelfAccess, Snapshot, sample
                 └─────▲──────┘
      ┌────────────┬───┴──────────┬──────────────┐
┌─────┴─────┐ ┌────┴─────┐ ┌──────┴──────┐ ┌─────┴──────┐
│  wh-nav   │ │wh-layout │ │ wh-storage  │ │  gui-core  │ ← зависит ещё от nav,
│ маршруты  │ │расстановка│ │ трейты+JSON │ │ редактор+UI│   layout, storage
└───────────┘ └──────────┘ └─────────────┘ └─────▲──────┘
                                           ┌─────┴──────┐
                                    app-editor      app-viewer
```

`wh-layout` намеренно **не** зависит от `wh-nav`: он принимает готовые `ShelfAccess`.
Благодаря этому алгоритм расстановки можно заменить и тестировать на синтетических оценках.

## 3. Модель данных (`wh-core::model`)

| тип | смысл |
|---|---|
| `Warehouse` | контур (`Polygon`), точка входа, список `Shelf` |
| `Shelf` | `OrientedRect` (центр, ширина, глубина, угол), `capacity`, `double_sided` |
| `Product` | `size` (ячеек), `demand: Option<f32>` |
| `Placement` | связка товар → стеллаж, флаг `pinned` (закреплено вручную) |
| `ShelfAccess` | результат анализа: расстояние, оценка 0..1, вершины маршрута |
| `Snapshot` | склад + товары + размещения — единица обмена (JSON, будущий сервер) |

Лицевая сторона стеллажа — локальная ось **+Y** прямоугольника; поворот `angle` вращает её
вместе с прямоугольником. `Warehouse::validate()` проверяет инварианты (контур простой, вход
внутри, стеллажи внутри контура и не пересекаются).

## 4. Геометрия (`wh-core::geometry`)

Всё написано вручную и без зависимостей, чтобы поведение на границах было предсказуемым.

* **`intersection_params(a,b,p,q)`** — параметры `t∈[0,1]` вдоль отрезка `a→b`, в которых он
  пересекает или касается `p→q` (для коллинеарных — концы перекрытия). Это основа остального.
* **`Polygon::contains`** — точка внутри *или на границе* (допуск 1e-7 м), затем чётно-нечётный луч.
* **`Polygon::contains_segment`** — отрезок целиком внутри, в том числе у невыпуклых контуров.
  Идея: собрать все `t` пересечений с рёбрами, отсортировать, проверить **середину каждого
  подотрезка**. Если оба конца внутри, но отрезок «срезает» вырез буквы L, одна из середин
  окажется снаружи.
* **`OrientedRect::segment_crosses_interior`** — отрезок против повёрнутого прямоугольника:
  переводим концы в локальную систему прямоугольника и режем по слэбам (Liang–Barsky). Рамка
  уменьшена на 1e-6, поэтому **скольжение по границе и касание угла не считаются пересечением** —
  это нужно, чтобы путь мог идти вдоль раздутого стеллажа.
* **`OrientedRect::overlaps`** — метод разделяющих осей; касание не считается пересечением.

Допуски (`EPS=1e-9`, `ON_EDGE=1e-7`, `1e-6` у рамки) — единственное «хрупкое» место. Если появятся
артефакты на очень больших или очень мелких планах, смотреть сюда в первую очередь.

## 5. Маршруты (`wh-nav`)

### 5.1. Идея

Кратчайший ломаный путь между двумя точками в многоугольнике с препятствиями всегда проходит
через **вершины препятствий и вогнутые углы контура**. Поэтому:

1. строим **граф видимости** на этих вершинах;
2. запускаем Дейкстру от входа;
3. любую целевую точку подключаем к тем вершинам, которые её «видят».

### 5.2. Построение графа (`Navigator::new`)

* **Препятствия** — стеллажи, раздутые на `clearance` (по умолчанию 0.4 м ≈ половина ширины
  прохода). Раздутый прямоугольник — снова прямоугольник, поэтому углов не нужно считать «миттером».
* **Вершины:** 4 угла каждого раздутого стеллажа + вогнутые вершины контура. Вогнутую вершину
  сдвигаем внутрь помещения по биссектрисе на `clearance / sin(θ/2)` (с ограничением), чтобы
  путь огибал угол с отступом, а не по самой стене.
* **Фильтр вершин:** выкидываем те, что вне контура или строго внутри чужого раздутого стеллажа
  (плотный ряд стеллажей с узким зазором так закрывает проход — это ожидаемо), и дубликаты.
* **Рёбра:** пара вершин соединяется, если `visible(a,b)` = нет пересечения с внутренностью
  препятствий **и** отрезок целиком внутри контура. Стоимость построения ≈ O(N²·(E+S)).
  Для сотен стеллажей — доли секунды; граф строится один раз на планировку.

### 5.3. Запрос (`routes_from` / `route_to`)

`routes_from(start)` делает Дейкстру от входа сразу до всех вершин и возвращает `RouteField`.
`route_to(target)`: если цель видна из входа — прямой отрезок; иначе перебираем вершины с
конечным расстоянием, берём ту, где `dist[v] + |v→target|` минимально и `v` видит цель, и
разворачиваем путь по массиву `prev`. Один `RouteField` обслуживает все стеллажи.

### 5.4. Оценка доступности (`analyze`)

Для каждого стеллажа берётся **точка доступа** — центр лицевой грани, отнесённый наружу на
`half_d + clearance + 0.01` (то есть на 1 см за границей раздутого стеллажа). У двусторонних
две точки, берётся ближайшая. Затем длины нормируются:

```
score = 1 − (d − d_min) / (d_max − d_min)      недостижимый → 0, все равны → 1
```

**Важная особенность:** оценка *относительная*. Добавление очень далёкого стеллажа меняет оценки
всех остальных. Для расстановки это нормально (важен порядок), для отображения «в процентах»
может удивлять. Если понадобится абсолютная шкала — заменить формулу в `accessibility.rs`
(например, `1/(1+d/d0)`); больше ничего менять не придётся.

## 6. Авторасстановка (`wh-layout`)

Жадный алгоритм, детерминированный (ничьи разрешаются по id):

1. Закреплённые (`pinned`) размещения сохраняются и занимают место; остальные отбрасываются.
2. Стеллажи: достижимые, по убыванию `score` (затем по расстоянию).
3. Товары: по убыванию `demand`, без `demand` — в конец.
4. Каждый товар целиком кладётся на **первый** стеллаж, где хватает свободных ячеек;
   не нашлось — попадает в `unplaced`.

Ограничения: нет деления партии между стеллажами, нет учёта совместимости/веса. Это самое
простое место для замены — сигнатура `auto_place(warehouse, access, products, existing)` не
зависит от остальных крейтов.

## 7. Редактор (`gui-core::editor`)

`EditorState` — единственный владелец данных проекта и «режима работы». Это конечный автомат:

```
Tool::Select   клик → выбрать стеллаж под курсором
Tool::Outline  клик → вершина (сетка 0.1 м + ортогональность); клик у первой → замкнуть
Tool::Shelf    клик → поставить стеллаж выбранного типоразмера (с проверкой fits)
Tool::Entrance клик → переставить вход (только внутри контура)
```

Ключевые правила:

* **Инвалидация анализа.** Любое изменение геометрии (стеллаж, вход, контур, двусторонность)
  делает `access.clear()`. Пустой `access` = «анализ устарел». `auto_place` сам пересчитает его.
* **Валидация при действии, а не постфактум.** Стеллаж не ставится и не поворачивается, если
  выходит за контур или пересекает соседа (`fits`).
* **`fit_requested`** — флаг «оболочка, впиши план в окно»; ставится после загрузки и замыкания
  контура, сбрасывается в `ui::App::push`.
* Метод `click(world, tol)` получает допуск в **метрах**; пересчёт из пикселей делает оболочка,
  поэтому сам редактор о пикселях не знает.

## 8. Отрисовка

### 8.1. Конвейер

```
EditorState ──► scene::build_2d / build_3d ──► Scene (строки команд, подписи)
                                                   │
                         ui::App::push ◄───────────┘   конвертирует в типы Slint
                                │
                         main.slint: слои Layer (Path) + Text + TouchArea
```

`Scene` — обычная структура без типов Slint: строки SVG-команд (`"M x y L x y … Z"`), цвета как
`Rgb`, подписи. Поэтому построение сцены покрыто тестами.

### 8.2. Почему Path и пиксели

В Slint нет канваса для произвольной векторной графики. Решение: компонент `Layer inherits Path`
на весь холст, с `viewbox-width/height` = размеру холста, то есть **координаты в командах = пиксели
холста**. Rust сам переводит метры в пиксели (`Viewport::to_screen`), Slint только рисует.
Слои снизу вверх: сетка → пол → маршрут → стеллажи (цикл `for`) → черновик контура → маркеры →
вход → подписи → «резиновая линия» → `TouchArea`.

Заметные детали:

* **Усик выдачи** — второй, *открытый* подконтур в той же строке команд, что и прямоугольник
  стеллажа (`… Z M x0 y0 L x1 y1`). Заливка его не затрагивает, обводка рисует короткую линию.
* **Черновик контура** разделён на два слоя — ломаную (без заливки) и маркеры вершин (с заливкой),
  потому что залитая незамкнутая ломаная закрашивала бы треугольник.
* **«Линейка» у курсора** целиком декларативная: линия и текст в `main.slint` читают
  `touch.mouse-x/y` и делят расстояние на `px-per-m`. Rust в движении мыши не участвует.
* **Сетка:** шаг выбирается из ряда 0.5…100 м так, чтобы линии шли не чаще, чем раз в ~14 px.
* **Тепловая окраска:** красный → жёлтый → зелёный по `score`; без анализа — нейтральный
  сине-серый; недостижимые — тёмно-красные.

### 8.3. Размер холста

Slint сообщает размер элемента только после раскладки, а колбэка «размер изменился» мы не
используем. Поэтому `main.slint` публикует `canvas-width/height`, а Rust читает их перед каждым
событием и раз в ~120 мс по таймеру; изменился размер — перерисовка (и «вписать», если пользователь
не менял масштаб руками).

### 8.4. Изометрия (`scene::build_3d`)

Проекция без перспективы:

```
sx =  (x − y) · cos30°
sy = −(x + y) · sin30° − z
```

Камера «смотрит с юго-запада»: ближе к зрителю — меньшие `x+y`.

1. Масштаб и центр подбираются по проекциям всех углов (пол и крыши).
2. **Порядок отрисовки** — алгоритм художника: стеллажи сортируются по `x+y` центра по убыванию
   (дальние первыми). Для непересекающихся прямоугольников этого достаточно.
3. **Видимые грани:** для каждого ребра берём внешнюю нормаль (у контура против часовой —
   правая нормаль `(dy, −dx)`); грань видна, если `normal · (−1,−1) > 0`. У стеллажа, повёрнутого
   кратно 90°, это две боковые грани + крыша.
4. **Освещение:** боковая грань затемняется по `normal · light`, крыша на 12 % светлее.
5. **Выбор кликом в 3D:** при построении сохраняется список экранных многоугольников всех граней
   в порядке отрисовки (`Scene::hit`); клик ищет **с конца** первую грань, содержащую точку
   (`point_in_poly`) — так выигрывает то, что нарисовано сверху.

Высота стеллажа пока константа `SHELF_HEIGHT` (2 м).

## 9. Связка со Slint (`gui-core::ui`)

* Любое событие проходит один и тот же путь: **синхронизация с окном** (размер холста, флажок
  «ортогонально») → действие над `App`/`EditorState` → `push` (полная перерисовка).
* Этот путь собран в макросе `wire!`. Он убирает ~25 одинаковых блоков `clone Rc / weak.upgrade /
  borrow_mut / push`. Если макрос кажется слишком хитрым — его можно заменить обычной
  функцией-обёрткой, поведение не изменится.
* Полная перерисовка: сцена строится заново на каждое событие. Для сотен стеллажей это дёшево;
  оптимизировать (инкрементальные модели) стоит только после измерений.
* Режимы Editor/Viewer — одно окно, свойство `editor-mode` скрывает панели редактирования;
  в Viewer инструмент принудительно `Select`.

## 10. Хранение

`wh-storage` содержит трейты `WarehouseRepository`, `CatalogRepository`, `PlacementRepository`
(+ `Storage` = все три), реализацию в памяти и `json::{save_file, load_file}` для `Snapshot`.
Сервер будущего этапа зависит только от трейтов; конкретная БД — отдельный крейт.

## 11. Как добавить…

| задача | где править |
|---|---|
| поле в модель (например, высота стеллажа) | `wh-core::model` → `scene` (3D) → `editor` (UI-ввод) |
| другой алгоритм расстановки | `wh-layout` (сигнатуру сохранить) |
| абсолютная шкала доступности | формула в `wh-nav::accessibility` |
| новый инструмент редактора | `Tool` + ветка в `EditorState::click` + кнопка в `main.slint` + `on_tool_selected` |
| перетаскивание стеллажей | `Tool::Move` в `editor`; нужны события move/press — расширить `TouchArea` |
| сервер | новый крейт `wh-server` над `dyn Storage`; DTO = типы `wh-core` с feature `serde` |

## 12. Технический долг (честно)

* `editor.rs` (~500 строк) смешивает инструменты рисования, каталог товаров, анализ и
  информационные строки. Естественное разбиение: `outline`, `shelves`, `catalog`, `analysis`.
* Константы разбросаны: `clearance 0.4`, допуск клика `12 px`, длина «усика» `0.4 м`, шаг сетки
  `0.1 м`, высота `2 м`. Стоит собрать в одну структуру конфигурации.
* Русские строки интерфейса и статусов вшиты в код (нет слоя локализации).
* Код `ui.rs` и `main.slint` не покрыт автотестами (проверяется только руками).
* Допуски геометрии — эмпирические (см. §4).
* Не настроены CI, `rustfmt`/`clippy`; не все публичные элементы имеют rustdoc.
* Часть кода писалась без возможности компиляции — первые версии могли содержать мелкие
  ошибки; исправления вносятся по мере прогона `cargo test`.
